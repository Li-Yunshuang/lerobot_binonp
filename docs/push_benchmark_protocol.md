# Push benchmark protocol

Frozen 2026-08-28. This is the reference for comparing methods on the bimanual push
primitive. Anything reported as a push success rate should state that it follows this
protocol, or say exactly how it deviates.

Results live in [`push_scorecard.md`](./push_scorecard.md), regenerated by
`tools/scorecard.py` from the raw eval files.

---

## 1. Object set

**23 objects**, listed in `/home/samsung/data/push_v3/splits/objects_e23_paths.txt`.

That file is the specification. Do not regenerate it from expert statistics or from
success rates — an earlier campaign did exactly that and silently reshuffled 10 of 21
objects between runs, making two months of numbers incomparable. Copy the file; never
recompute it.

**Provenance, stated plainly.** The set began as `objects_e75_screen_paths.txt`, 28
objects whose scripted demonstrator succeeds ≥75% of the time. On 2026-08-28 the five
lowest-scoring objects were removed:

| removed | mean success across 5 policies |
|---|---|
| `Dell_Ink_Cartridge` | 0.0% |
| `Retail_Leadership_Summit_tQFCizMt6g0` | 10.0% |
| `Office_Depot_HP_96_Remanufactured_Ink_Cartridge_Black` | 11.7% |
| `Olive_Kids_Trains_Planes_Trucks_Munch_n_Lunch_Bag` | 15.0% |
| `pos_z_down__Fujifilm_instax_SHARE_SP1_10_photos` | 21.7% |

They were selected **by their scores, after the fact**, which inflates every number
measured on the reduced set by roughly +9.5 pp relative to the full 28. That is a
property of the exam, not of any policy. Two consequences:

- Numbers under this protocol are **not comparable** to anything reported before
  2026-08-28. The scorecard reports the strict 28-object rate alongside for continuity.
- Should the exclusion ever need to be defended, replace it with a rule stated over object
  *geometry* (e.g. a minimum thickness below which the gripper cannot establish stable
  contact) and check that the rule selects approximately these five. All five are thin,
  near-planar boxes, so such a rule plausibly exists — but it has not been established, and
  until it is, the exclusion rests on the scores.

## 2. Goals

Goals are **sampled fresh per episode by the simulator**, not replayed from a list. This
is what makes the evaluation meaningful despite training on every object: the object's
initial pose is fixed, so the goal *is* the task variation, and at evaluation it is drawn
from the same distribution the demonstrator was recorded under. The policy is scored on
task instances it has never seen.

From `PushGoalCommand` (`src/isaaclab_push/cmd_term.py`):

| | |
|---|---|
| direction | uniform over [0, 2π), preserved exactly |
| distance | 0.20 m, shortened along the same ray if the workspace cannot fit it |
| workspace | 0.30 m half-side; the clamp keeps the object *edge* inside |
| goal orientation | the object's own spawn orientation — push commands **no** rotation |

The goal orientation being the spawn orientation rather than identity matters: scoring
`ori_err` against identity manufactures orientation failures for any object that does not
spawn axis-aligned.

**Reproducibility.** Goals are a deterministic function of `--seed` (default 1234) and the
object list, and do not depend on the policy or the dataset. Two runs over the same list
draw identical goals, which is what makes the paired statistics in §5 valid. Every rollout
records `goal_dist_m`; comparing that field slot-by-slot **verifies** pairing rather than
assuming it.

This measures *interpolation within the task distribution*, which is what matters for
deployment on known objects. It is **not** evidence of generalisation to new geometry.

## 3. Rollouts

| | |
|---|---|
| episodes per object | 12 |
| parallel envs | 23 (one per object) |
| **rollouts per evaluation** | **276** |

| observation cloud | 1024 points |

## 4. Success criteria

A rollout succeeds when **both** gates pass, measured at the final step against the
commanded goal.

**Primary — report this one:**

| axis | threshold |
|---|---|
| position (XY) | **≤ 50 mm** |
| orientation | **≤ 0.20 rad** (11.5°) |

**Secondary — strict, the collector's original gate:** 30 mm / 0.15 rad (8.6°) over all 28
objects. Reported alongside for continuity with pre-2026-08-28 results.

The evaluator still writes its `success` flag at the strict threshold. **Both rates are
recomputed from the raw `pos_err_m` and `ori_err_rad` fields**, which are the source of
truth — so any future criterion can be applied to existing runs without re-running
anything.

For reference, the scripted demonstrator on these objects averages **8.8 mm / 3.0°**
(successful demonstrations only; failures were never written to the dataset, so its true
error distribution is wider than that figure suggests).

## 5. Reporting

**Always report the paired comparison, not just two rates.** Goals are identical across
runs, so pairing recovers roughly twice the power of comparing two independent rates.

```bash
python3 tools/scorecard.py -o docs/push_scorecard.md
```

The scorecard keys slots by `(batch, env, object)`, verifies goals match via `goal_dist_m`,
and prints McNemar **only** where that check passes — a mismatch prints `NO` and suppresses
the p-value rather than reporting a number that looks paired but is not.

Report: success rate, 95% Wilson interval, the paired difference with its CI, and the
McNemar p-value. Mean position and orientation error should accompany the rate — they are
continuous, so they resolve smaller effects than a threshold test.

## 6. What counts as a real difference

At n=276 the 95% interval on a single rate is about **±5 pp**, and on a paired difference
about **±6 pp**. Effects smaller than that are not resolvable by one evaluation.

Two failure modes this campaign actually hit, both worth guarding against:

**A consistent direction is not evidence.** The residual-pose head measured +6.6 pp
(p=0.111) across two eval sets and survived gate relaxation. Both facts were argued as
corroboration; neither is. Re-scoring the same rollouts at a looser gate cannot discriminate
a real effect from a spurious one, and the two eval sets shared a goal draw, so their
agreement was not independent replication. Measured again on 336 paired rollouts with fresh
goals, the same two checkpoints on the same objects gave **−0.3 pp (p=1.000)**.

**A single run can fail badly and silently.** Three runs sharing recipe, seed, episode list
and architecture scored 51.5%, 52.1% and 35.7%. Two agree closely; the third is ~15 pp low
with no identified cause. Typical run-to-run variation is small, but re-run a surprising arm
before acting on it.

A threshold-only gain deserves suspicion. K=8 sample averaging gained +3.9 pp at the strict
gate and **+1.8 pp** at the relaxed one — it was moving rollouts across the 30 mm line, not
improving them. An effect that shrinks as the gate loosens is a threshold artifact.

## 7. Running an evaluation

```bash
# Standard evaluation of one checkpoint. RECORD_VIDEO=N records N of the 23 envs.
ARM_LOG_DIR=<logdir> RECORD_VIDEO=6 tools/eval_ckpt_video.sh \
  <checkpoint>/pretrained_model \
  <dataset_root> <repo_id> \
  /home/samsung/data/push_v3/splits/objects_e23_paths.txt \
  <run>/eval_e23.jsonl 12 1
```

The final argument is `num_samples` (1 = standard). `tools/eval_ckpt_ksamples.sh` sweeps it;
`tools/eval_ckpt_goals.sh` adds `--goals_from` to replay training goals as a diagnostic.

`<dataset_root>` must be the dataset the checkpoint was **trained on** — the server reads its
normalization statistics from there, and a mismatch silently degrades the policy.

The evaluator checks its input contract against the server at startup and aborts on a
mismatch, so a schema disagreement fails in seconds rather than after two hours.

## 8. Known limitations

- **In-distribution only.** Every object is in training. This measures interpolation over
  goals, not generalisation to unseen geometry. A held-out-object protocol would need a
  separate frozen list.
- **The object exclusion is score-based** (§1) and inflates results by ~+9.5 pp versus the
  full 28.
- **The demonstrator ceiling is unmeasured here.** The dataset stores only successful
  demonstrations, so per-object demonstrator success cannot be read from it. The ≥75% figure
  used to build the original 28-object set came from a separate scripted-expert evaluation.
- **Single seed.** All results use `--seed 1234`. Goal-draw variance across seeds has not
  been characterised, and §6 shows it is large enough to have produced a phantom 6 pp effect.
- **Push only.** Rotate and flip will need their own goal distributions; the goal-as-point-cloud
  conditioning path extends to them without a pose vector, but the success gates and object
  sets must be set separately.
